# homer-tui

Терминальный интерфейс к Homer 7 через REST API homer-app (`/api/v3`), тот же, на котором работает веб-интерфейс Homer: поиск SIP-звонков, регистраций и логов, звонок лесенкой, QoS по RTCP, выгрузка PCAP и текста, импорт PCAP, настройки Homer. Несколько инстансов Homer рядом, клавиши vim, темы, интерфейс на английском или русском.

English version: [homer-tui.md](homer-tui.md).

## Что видно сверх веб-интерфейса

### Звонок, который возвращается, в развёрнутом виде

Лесенка с одной колонкой на хост, как её рисует веб-интерфейс Homer, гоняет звонок, который возвращается через те же хосты, туда и обратно по тем же колонкам. Частый случай - PBX, который переадресует звонок наружу через тот же SBC, откуда он пришёл: второй INVITE идёт влево, ответы на него вправо, и оба плеча перемешиваются на одних дорожках. homer-tui такой звонок разворачивает: хост, на который звонок вернулся, рисуется ещё раз правее, поэтому звонок читается слева направо в том порядке, в каком шёл, и каждый запрос идёт вправо. Так же разворачивается B2BUA с внешним и внутренним адресом, а PBX, который звонит двум сторонам и бриджует их, стоит между своими звонками. В заголовке видно `unfolded`; `u` рисует каждый хост один раз, а `flow: {unfold: false}` в конфиге делает это поведением по умолчанию. Правила описаны в разделе [Клавиши](#клавиши).

Каждый хост один раз, как в веб-интерфейсе:


### RTCP как путь медиа

Веб-интерфейс показывает RTCP графиками каждой величины по потокам. На вкладке QoS звонка `v` в homer-tui показывает вместо этого путь медиа: хосты медиа в порядке звонка, построенные по offer и answer в SDP, и на каждом участке, для каждого направления звука, MOS и худшие потери, о которых сообщил получатель, цветом «хорошо», «средне» или «плохо». Участок, о котором никто не сообщает, рисуется без данных, а прокси, через который медиа не идёт (SBC ниже), стрелка перешагивает. Под схемой сводка словами говорит, что слышит каждая сторона и где начинается проблема: для каждого направления первый участок, где звук портится, потому что то, что сломалось там, тянется на следующие участки. Over time рисует MOS каждого участка по ходу звонка. `flow: {qosGraphs: true}` в конфиге открывает вкладку сразу в этом виде.

## Сборка

Нужен Go 1.22+.

```sh
make build            # ./bin/homer-tui и ./bin/homer-tui-mock
make test
make install          # в $GOPATH/bin
```

## Подключение

Конфиг лежит в `~/.config/homer-tui/config.yaml` (или `$HOMER_TUI_CONFIG`). Пример печатает `homer-tui -sample-config`:

```yaml
currentHost: prod          # the host to start on, default: the first one
theme: default             # :theme lists them, custom ones below
# language: ru             # interface language (en, ru), default: from LANG; :lang switches
downloadDir: ~/Downloads   # where PCAP and text exports are saved
defaultSince: 1h           # search window when a query gives none
defaultLimit: 200
refreshSeconds: 5          # auto-refresh period (a in search results)
# flow:                    # how a call opens; f, a, u, v change it until homer-tui quits
#   hide: [LOG]            # kinds not to show: SIP, RTCP, LOG, "HEP 54"
#   byAlias: true          # one lane per alias instead of per address
#   unfold: false          # each host once, even when a call comes back
#   qosGraphs: true        # the QoS tab as graphs instead of a table
# searchFields:            # the fields of the search form by profile; ctrl-a, ctrl-d change them until homer-tui quits
#   1_call: [from_user, to_user, callid, user_agent]
hosts:
  - name: prod
    url: https://homer.example.com
    username: admin
    passwordCmd: security find-generic-password -s homer-prod -w
    labels: {dc: dc1, env: prod}   # or a plain tag: labels: prod, or a list: [prod, dc1]
  - name: lab
    url: http://127.0.0.1:9080
    username: admin
    password: sipcapture
  - name: ci
    url: https://homer.example.com
    tokenCmd: security find-generic-password -s homer-ci-token -w   # or token: <Auth-Token from :tokens>
    insecure: true          # do not verify TLS
    # apiPrefix: /homer     # when homer-app runs with main_settings.apiprefix
    # timezone: Europe/Berlin   # the zone to show times in
themes:
  noc:
    base: nord             # start from a built-in theme
    accent: "#ffaf00"
```

Без конфига: `HOMER_PASSWORD=... homer-tui -url http://homer:9080 -user admin` или через `HOMER_URL`, `HOMER_USER`, `HOMER_TOKEN`. `-password` и `-token` тоже работают, но их видят в `ps` другие пользователи машины; переменные окружения и `passwordCmd`/`tokenCmd` не видны. Такой хост добавляется под именем `cli` рядом с настроенными.

Вход: по логину и паролю homer-tui получает JWT (`POST /auth`) и сам входит заново, когда тот истекает. `passwordCmd` получает пароль командой, например из связки ключей. Вместо пароля у хоста может быть `token`: он уходит в заголовке `Auth-Token` (`tokenHeader` меняет имя) и работает, только если в homer-app включено `api_settings.enable_token_access`; `tokenCmd` получает его командой, как `passwordCmd` пароль. Токенам homer-app даёт права обычного пользователя, поэтому для изменения настроек нужны логин и пароль администратора. Если сервер отклоняет токен (HTTP 401), значит, токен истёк, удалён, исчерпал `limit_calls`, или вход по токенам выключен. `:tokens` под администратором показывает EXPIRES, CALLS и LIMIT и создаёт новый токен, его секрет показывается один раз.

Учётные данные уходят только на настроенный хост: перенаправление на другой хост или с https на http отклоняется с ошибкой, потому что Go перенёс бы туда заголовок `Auth-Token` и пароль из `POST /auth`. `url` с пользователем или паролем внутри не принимается, потому что адрес виден на экране: их место в `username` и `password`. Если конфиг с `password` или `token` доступен на чтение другим, об этом говорит шапка (`Auth:` … `chmod 600`). Экспорт PCAP и текста, где есть номера и SIP, сохраняется только для владельца (права 600) и никогда поверх существующего файла: второй получает `-1`.

При запуске каждый хост входит в фоне. Хост, который не пускает или не отвечает, пишет причину в списке хостов, остальные работают. Экран хоста, который ещё не ответил, показывает «подключение к …» и открывается сам, когда тот ответит.

Флаги: `-host prod` - стартовый хост, `-c 'calls from_user=100 since=2h'` - стартовая команда, `-theme nord`, `-lang ru`, `-download-dir`, а также `-url`, `-user`, `-password`, `-token`, `-insecure` для хоста без конфига.

## Хосты

В шапке - текущий хост и его URL, пользователь и роль, узлы БД, способ входа и сборка. homer-app не сообщает свою версию через API, поэтому строки с версией, как в rtpengine-tui и opensips-tui, нет.

`:hosts` показывает список хостов: адрес, способ входа, пользователь и роль, статус входа, узлы БД и метки. Текущий хост отмечен `*`: это `currentHost` из конфига, а без него первый в списке. С одним хостом homer-tui сразу открывает его звонки, с несколькими начинает со списка. В списке `enter` открывает звонки хоста, `space` делает хост текущим, `d` открывает его карточку, `r` входит заново. `:<имя хоста>` переключает на хост с любого экрана и открывает там тот же поиск, те же настройки или карточку.

Карточка хоста (`:info`): URL, префикс API, пользователь и роль, администратор ли он, TLS, часовой пояс; узлы БД; модули (`/modules/status`); типы авторизации (`/auth/type/list`); профили поиска из маппингов. `y` переключает её на JSON и обратно.

## Клавиши

| Клавиша | Действие |
|---|---|
| `j` `k` `g` `G` | вниз, вверх, в начало, в конец |
| `ctrl-d` `ctrl-u`, `ctrl-f` `ctrl-b` | полстраницы, страница |
| `H` `M` `L`, `h` `l` | верх, середина, низ экрана; прокрутка колонок |
| `enter`, `esc` или `q` | провалиться внутрь, вернуться назад |
| `:` | командная строка (дополнение по `tab` и стрелкам, с историей) |
| `/` | фильтр строк (regex, `!` в начале инвертирует); в тексте - поиск, затем `n` `N` |
| `space` | отметить строку: звонок, PCAP и экспорт работают по отмеченным |
| `o` `O` | колонка сортировки, обратный порядок |
| `ctrl-r` | обновить |
| `?` | справка |
| `:q`, `ctrl-c` | выход |

Результаты поиска: `enter` открывает звонок отмеченных или текущей строки, `v` переключает вид между сессиями и отдельными сообщениями, `d` - карточка строки (сессия со статусом, длительностью и сообщениями или одно сообщение с его полями), `y` - строка в JSON (повторный `y` закрывает), `s` - форма поиска, `e` - запрос в командной строке, `[` `]` сдвигают окно времени, `a` - автообновление, `p` - PCAP, `t` - текст.

Экран звонка: `1`-`4` или `tab` переключают вкладки Лесенка, Сообщения, QoS, Логи. `enter` показывает сообщение целиком, `z` скрывает панель сообщения, `h` `l` или стрелки сдвигают лесенку на один хост, когда хосты не помещаются (в заголовке видно, какие показаны), `0` `$` - к первому и последнему, `p` `t` выгружают PCAP и текст, `y` - сообщение в JSON (повторный `y` закрывает).

Строка под вкладками, отделённая от них линией, говорит, чем кончился звонок, по плечу его первого INVITE, как его видел вызывающий: финальный ответ своим цветом (или последний предварительный, или «no answer»), затем метки своим цветом со значением белым на фоне того же цвета:

| Метка | Значение |
|---|---|
| `RNG` | через сколько пошли гудки: от INVITE до первого 180 или 183 |
| `ASW` | через сколько ответили: от INVITE до 200 |
| `RBT` | сколько шли гудки, если звонок отменили до ответа |
| `DUR` | разговор от ответа до BYE; с `…`, пока `F` следит за идущим звонком |
| `BYE` | кто положил трубку: вызывающий или вызываемый; `нет`, если у отвеченного звонка нет BYE |
| `CXL` | кто отменил |
| `RSN` | Reason из BYE или CANCEL, причина Q.850 по названию |
| `LEG` | SIP-плечи звонка |

Дальше - кто кому звонил. Через прокси учитываются ответы, которые получил вызывающий; Reason, который прокси не передал, берётся с других участков того же запроса.

```
 200 OK RNG 1.07s ASW 3.09s DUR 1m3s BYE вызывающий LEG 2 114 → 217
 487 Cancelled RNG 840ms RBT 4.84s CXL вызывающий LEG 1 102 → 201
 486 Busy LEG 1 102 → 216
```

Колонка `TX` рядом с лесенкой показывает SIP-транзакции: скобка от первого сообщения транзакции до последнего (`┌` `├` `└`, `╶` - транзакция из одного сообщения), цвета чередуются. Транзакция - это сессия и CSeq, поэтому участки одного запроса через прокси - одна транзакция, а ACK на неуспешный INVITE относится к INVITE; ACK на 2xx - отдельная транзакция. Транзакции, открытые одновременно (PRACK или CANCEL, пока INVITE ждёт ответа), стоят в соседних колонках.

`v` показывает SIP-сообщение понятным языком вместо исходного текста и обратно: стороны (request URI, From, To, P-Asserted-Identity, Diversion и подобные), маршрут от первого узла (Via и Record-Route с алиасами Homer), медиа из SDP с кодеками по именам и пометкой удержания, правила сессии (Session-Expires, Require, Supported, Allow) и итог: ответ с тем, что он обычно значит, Reason с причиной Q.850 по названию, Warning. Выбор сохраняется для следующих звонков до выхода из homer-tui; `enter` открывает сообщение целиком в том же виде, и `v` переключает вид и там. `m` переводит фокус в панель сообщения, чтобы её прокручивать (`j` `k`, `g` `G`, `ctrl-d` `ctrl-u`, `ctrl-f` `ctrl-b`, там же работает `v`); `m`, `esc` или `q` возвращают к списку.

На вкладке QoS `v` показывает RTCP-отчёты как путь медиа вместо таблицы. Сверху схема как лесенка: хосты медиа в порядке звонка, вызывающий слева, по имени хоста, который объявил их адреса в SDP; релей с двумя адресами, например rtpengine за SBC, - одна колонка. Под именем колонки её IP, у релея оба, так что внутренний и внешний адреса различаются. Каждый SIP-участник звонка - колонка, шлёт он RTCP или нет, а участки берутся из оффера и ответа в SDP, поэтому участок без отчётов рисуется с «нет данных», а над прокси, через который медиа не идёт, стрелка проходит насквозь. Колонки - это дорожки лесенки по алиасам и с раскрытием: у звонка, который возвращается через те же хосты (например, переадресация с PBX), медиа идёт по своим колонкам правее, и звук к вызываемому тоже идёт вправо. Строка «слышит вызываемый» - звук в сторону вызываемого, «слышит вызывающий» - обратно; каждая стрелка - участок и то, что сообщил его получатель: MOS и худшие потери с оценкой хорошо, средне или плохо, или «нет данных», если получатель отчётов не шлёт (rtpengine обычно не шлёт). Все SSRC одного направления - одна стрелка, re-INVITE её не дробит. «Итог» словами говорит, что слышит каждая сторона, по отчёту соседнего с ней участка или ближайшего, и где проблемы: для каждого направления первый по ходу звука участок, где он портится, потому что то, что ломается там, переходит на участки после него, или что проблем не видно и какие участки не прислали отчётов. «По времени» рисует MOS каждого участка с отчётами по ходу звонка тонкой линией, цвет которой меняется от зелёного через жёлтый к красному, `·` - отчётов нет, цифры справа. Панель сообщения под схемой перечисляет участки с адресами и объясняет вид.

На вкладке Logs `w` показывает логи целиком: у каждого время и адреса, а сообщение переносится по ширине экрана, вместо таблицы, где сообщение обрезано; повторный `w` возвращает таблицу.

`F` следит за звонком, который ещё идёт: он перезагружается на каждом тике (`refreshSeconds`), а окно запроса продлевается до текущего момента. Выделение остаётся на своём сообщении, а если стояло на последнем, переходит на новые; в заголовке пометка `live`. Слежение выключается само, когда на BYE пришёл ответ или INVITE не прошёл, и сообщает об этом; повторный `F` тоже выключает.

homer-app кладёт в лесенку звонка SIP, RTCP и HEP-логи вместе. `f` выбирает, что из этого показывать, с числом сообщений каждого вида (SIP, RTCP и LOG есть в списке всегда, с нулём, если в звонке их нет): `space` или `enter` включает и выключает строку, `esc` возвращает к звонку. Дорожка лесенки - это один IP и порт; `a` собирает все адреса одного алиаса в одну дорожку, и во второй строке заголовка видно, сколько их (`f` показывает, сколько дорожек останется).

Звонок со скоррелированными плечами может вернуться: A звонит в Б, Б в В, потом В звонит в Б, а Б в A. homer-tui такой звонок раскрывает. Плечо - это сообщения одной сессии между двумя хостами, его первый запрос идёт слева направо, и если этот запрос идёт к хосту, который есть только левее отправителя, хост рисуется ещё раз справа. Звонок тогда читается слева направо как A, Б, В, Б, A, и INVITE от В к Б идёт вправо, а не обратно влево; в заголовке видно `unfolded`. Устройство с двумя адресами под одним алиасом, например B2BUA с внешним и внутренним интерфейсом, раскрывается по обоим: если звонок вернулся на один адрес и уходит с другого, другой тоже рисуется ещё раз. PBX, который звонит двум сторонам и бриджует их (например, Asterisk, набирающий один канал, а затем другой), стоит между своими звонками: первый идёт вправо, второй, который самый левый хост начинает после первого, - влево, и всё, что следует за ним, тоже уходит влево. Направление плеча задаёт его первый запрос, даже если ответ на него другой агент записал чуть раньше. Ответы и запросы внутри плеча идут по его дорожкам, RTCP и логи - по самым правым дорожкам своих хостов. Звонок, который не возвращается, выглядит одинаково в обоих режимах. `u` рисует каждый хост один раз.

Фильтр, `a` и `u` действуют на вкладки Лесенка и Сообщения и сохраняются для следующих звонков до выхода из homer-tui. В конфиг они не пишутся. При запуске звонки открываются так, как задано в `flow:` конфига (`hide`, `byAlias`, `unfold`, см. пример выше), а без него - со всеми сообщениями, хостами по адресам и раскрытием. `qosGraphs: true` там же открывает вкладку QoS графиками; `v` переключает её на таблицу и обратно, и это тоже сохраняется до выхода из homer-tui.

Настройки: `d` и `enter` - карточка записи, `y` - её JSON (повторный `y` закрывает), `e` - правка в `$EDITOR` (по порядку: `HOMER_TUI_EDITOR`, `VISUAL`, `EDITOR`, `vi`), `c` - создать из шаблона (редактор должен ждать закрытия файла: если он вернулся сразу, как `code` без `--wait`, ничего не сохранится, и homer-tui об этом скажет; шаблон, сохранённый без изменений, создаётся после вопроса), `shift-d` - удалить с подтверждением. Для алиасов `shift-t` включает и выключает алиас, для маппингов `x` сбрасывает маппинг к встроенному.

### Маппинги

Маппинг (`:mappings`, таблица `mapping_schema` в homer-app) описывает для homer-app один вид сообщений: ключ `hepid_profile` (`1_call`) задаёт таблицу, где они лежат (`hep_proto_1_call`), поля - что можно искать, корреляция - с чем собирается найденный там звонок. Список говорит это коротко: что за сообщения, полезная нагрузка и профиль (`SIP · call`, `LOG · default`, `RTP · default`), сколько полей поиска, ЛЕСЕНКА - из чего собирается лесенка найденного там звонка (`LOG`, `RTCP`, `RTP`, `SIP`, `LEG` - другие плечи), ищет ли homer-app этот профиль и сколько проблем нашёл homer-tui. `enter` или `d` открывает карточку маппинга (искать по профилю - `:search 1_call …`):

- Что это: полезная нагрузка (SIP, RTCP, RTP, LOG), профиль, как сервер захвата раскладывает сообщения (call, registration, default), таблица, и ищет ли её homer-app: только при `partid` 10.
- Поля поиска: имя, которое пишется в поиске (`from_user=100`), и поле, за которым оно стоит (`data_header.from_user`). `sid`, `raw`, `id` и `create_date` ищутся в любом профиле; любое другое поле, которого нет в списке, homer-app молча выбрасывает из поиска.
- Лесенка: из чего состоит лесенка найденного здесь звонка, по блокам, как в конструкторе (`b`): сначала собственные сообщения звонка, затем по строке на правило в том виде, как их запишет `s` в конструкторе, блок плеч первым. В строке - что правило добавляет, словами списка (`LOG` - логи с этим Call-ID, `RTCP` - RTCP-отчёты с этим Call-ID, `RTP`, `SIP` - SIP с этим Call-ID, `LEG` - другое плечо звонка и как оно находится), в каком маппинге ищет, `append_sid` у правила, которое передаёт найденные id сессий дальше, и `✗` с причиной, если homer-app правило в нынешнем виде пропускает, падает на нём или ничего не находит. Слева - номера правил homer-app, которые стоят за строкой, те же, что в проблемах сверху; два номера - одно правило дважды, например логи до правила с `append_sid` и снова после него, здесь они выполняются один раз. Если конструктор записал бы правила иначе, карточка говорит, сколько их будет. Правило, которому не соответствует ни один блок, говорит, какое поле с каким сравнивает. Под строками - насколько раньше и позже окна поиска ищут правила, если у всех одинаково. Точный JSON - по `y`.

- Только хранится: `retention`, `partition_step`, `version`, `hep_alias`. homer-app их не читает; у сервера захвата могут быть свои настройки.
- Проблемы, сверху: что homer-app пропускает, читает неверно или на чём падает. `partid` не 10; `_` в профиле, который ломает сборку звонка, потому что homer-app режет ключ по первому `_`; недопустимые символы в ключе; два маппинга с одним ключом; поля, которые он отвергает (принимает только `data_header.имя` и `protocol_header.имя`); правила без `source_field`, `lookup_id` или двух чисел в `lookup_range`, на которых homer-app падает; `lookup_id` 0, который он пропускает; пустой `input_function_js`, который homer-app выполняет и падает (ключ нужно убрать; конструктор пустые ключи не пишет); `source_field`, которого нет в профиле, с именем, под которым поле есть в его таблице (`correlation_id` - это `protocol_header.correlation_id`, а не `data_header`); `lookup_field` вида `data_header.callid`, который не SQL и ничего не находит (он есть во встроенном `100_default`: правильно `data_header->>'callid'`); правило, повторённое без правила с `append_sid` между ними, которое передало бы новые id сессий.

`b` собирает сборку звонка маппинга из блоков вместо JSON. Блоки - это то, ради чего пишутся правила, они названы так же, как в лесенке, а список показывает для каждого профиль, где он ищет, СОВПАДЕНИЕ (MATCH) - что он берёт из звонка, ИЩЕТ В (LOOKUP) - в каком поле ищет это там, и окно:

```
ON  BLOCK  PROFILE  MATCH             LOOKUP          WINDOW
✓   LOG    default  Call-ID           sid             5m before, 3m20s after
✓   RTCP   default  Call-ID           sid             5m before, 3m20s after
✓   LEG    call     correlation_id    Call-ID         5m before, 3m20s after
✓   LEG    call     Call-ID+"_b2b-1"  Call-ID         5m before, 3m20s after
```

`append_sid` после поля поиска отмечает блок, чьё правило передаёт найденные id сессий правилам после него, чтобы те искали и по ним. `LOG` и `RTCP` приносят логи и RTCP с Call-ID звонка; `RTP` - отчёты RTP-агента по Call-ID или по IP сообщений; `SIP` - SIP профиля с тем же Call-ID, для лога или отчёта это его звонок; `LEG` - другое плечо: по `correlation_id` к `correlation_id` - другие плечи B2BUA с тем же `correlation_id` со всеми их сообщениями, и все остальные блоки работают и для них; по `correlation_id` к `Call-ID` - плечо, чей Call-ID - `correlation_id` этого звонка (X-CID); по `Call-ID+"суффикс"` - плечо, чей Call-ID - этот плюс суффикс, например `_b2b-1` у Asterisk. Своё правило остаётся как есть и правится как JSON. Блоки одинаковы для всех маппингов; каждый берёт Call-ID оттуда, где его хранит таблица маппинга: `data_header.callid` в SIP-таблицах и id сессии `sid` в таблицах логов, RTCP и RTP-отчётов. `space` включает и выключает блок, `enter` или `e` настраивает его (окно вокруг поиска, профиль, где искать, суффикс), `a` добавляет блок после настройки (под списком блоков - полное описание выбранного) (`esc` в настройке возвращает к списку блоков и ничего не добавляет), `shift-d` удаляет после вопроса, `shift-j`/`shift-k` двигают (блок плеч по `correlation_id` остаётся первым: найденные им id сессий получают блоки после него); под блоками homer-tui показывает, как соберётся звонок и на чём споткнётся homer-app, а `s` сохраняет после вопроса, где видно число правил до и после. `esc` спрашивает перед выходом, только если блоки меняли здесь; если блоки маппинга как он есть записывают правила иначе (повторы свёрнуты, плечи первыми, сломанный `lookup_field` исправлен), об этом говорит строка под ними, и `s` запишет их так. При чтении маппинга конструктор превращает правила, повторённые после правила плеч, в один блок и пишет правило плеч первым, поэтому маппинг, где девять правил ищут логи, RTCP и плечи дважды, сохраняется шестью правилами с тем же результатом; сломанный `data_header.callid` у `100_default` записывается как `data_header->>'callid'`.

homer-app читает маппинги на каждом поиске, поэтому изменение действует сразу. Его обновление записывает только непустые и ненулевые поля, поэтому `e` отправляет маппинг целиком.

## Команды

| Команда | Что делает |
|---|---|
| `:calls [фильтры]` | поиск звонков, профиль `1_call` |
| `:reg`, `:sip`, `:logs` | профили `1_registration`, `1_default`, `100_default` |
| `:search <hepid_profile> [фильтры]` | любой профиль из маппингов, например `:search 5_default`; можно и просто имя профиля |
| `:aliases` `:users` `:tokens` `:mappings` `:hepsub` `:advanced` `:usersettings` `:agents` `:dashboards` `:nodes` | настройки Homer |
| `:hosts [имя]`, `:host`, `:ctx` | список хостов или переключение; `:<имя хоста>` тоже переключает |
| `:info`, `:describe` | карточка хоста |
| `:import <file.pcap>`, `:import-now <file.pcap>` | загрузить PCAP в Homer, с исходным временем или со сдвигом на текущее |
| `:theme [имя]` | сменить тему, без имени - список |
| `:lang [en\|ru]` | язык интерфейса; без аргумента показывает текущий |

## Синтаксис поиска

```
:calls from_user=100 to_user=200 since=2h limit=500
:calls callid=abc@host                  поле по id, короткому имени или названию
:calls method=INVITE;BYE                ; - любое из значений
:calls from_user=10%                    % - LIKE
:calls user_agent!=friendly-scanner     != - отрицание
:calls from="2026-10-06 10:00" to=11:30 абсолютное окно; также -3h, RFC3339, unix
:reg node=node1,node2 or                узлы БД, OR между условиями
:calls since=1d where data_header.from_user = '100' AND data_header.method = 'INVITE'
```

В форме поиска (`s`) есть профиль, окно и несколько полей профиля: для звонков From user, To user, CallID и RURI user; для регистраций From user, CallID, Source IP и User Agent; для остальных профилей первые три поля, которые маппинг не скрывает. Окно - это длительность назад от текущего момента или диапазон: `1h`, `15:00..15:30`, `-3h..-1h`, `2026-10-21 16:00..` (до текущего момента). `enter` в любом поле или `ctrl-s` запускает поиск, `ctrl-c` очищает значения (поля остаются). `ctrl-a` добавляет другое поле профиля или опцию: Limit, Nodes, OR logic, Where (smart); `ctrl-d` убирает поле вместе со значением. Набор полей сохраняется для профиля до выхода из homer-tui; `searchFields` в конфиге задаёт его с запуска (поле по id, короткому имени или названию, как в запросе), а о поле, которого нет в маппинге, homer-tui предупредит. Поле со значением есть в форме всегда, поэтому запрос с `ua=` откроет её с User Agent.

homer-app ищет без сортировки: если в окне больше сообщений, чем `limit`, он отдаёт самые старые, то есть первые минуты «последнего часа». Поэтому homer-tui читает окно с конца, по частям, по мере прокрутки таблицы: первая часть - самый поздний отрезок окна, который `limit` вмещает целиком, а когда курсор подходит к последним строкам (`j`, `ctrl-d` или `G`), читается отрезок перед ним, и его строки добавляются в таблицу, курсор остаётся на месте. Строки сразу заполняют экран; пока есть ещё, заголовок говорит, до какого момента они загружены (`загружено до 16:47:05, дальше ниже`). Длину отрезка homer-tui подбирает несколькими поисками, деля пополам промежуток между длиной, которая влезает в лимит, и длиной, которая не влезает, чтобы в части было не меньше половины `limit`, если в окне столько есть. Часть состоит из целых сессий: это сессии с сообщениями в её отрезке, которых нет в более поздних частях, каждая со всеми своими сообщениями в окне. Поэтому статус, длительность и число сообщений верны, даже если сессия выходит за отрезок. Так сессия попадает в часть своей последней активности и в таблицу один раз. Эти сообщения приходят вторым поиском по id сессий, с теми же фильтрами, что и часть, где сессия целиком. Строки отсортированы по START (DATE для отдельных сообщений), сначала самые свежие, `o` и `O` это меняют; звонок, начавшийся раньше, а закончившийся позже прочитанных, встаёт среди них на место по своему START. Так работает любой поиск: `:calls`, `:registrations`, `:logs` и любой профиль. Сессия здесь - это id сессии, у SIP это Call-ID; строка без него, например лог не от звонка, идёт сама по себе. `r`, автообновление, `[` `]`, форма поиска и новый запрос читают окно заново с конца.

Статус сессии - это ответ на её запрос: первый финальный для звонка и последний для регистрации, которая обновляется. 401 или 407 просят учётные данные, и запрос приходит снова, поэтому статусом они становятся, только если ничего другого запрос не получил; ответы на другие запросы (BYE, PRACK) не учитываются.

Поля берутся из `fields_mapping` профиля (`:mappings`, затем `f`). homer-app молча отбрасывает поля, которых нет в маппинге, поэтому homer-tui предупреждает о незнакомых полях.

## Язык интерфейса

Интерфейс на английском и русском. Язык берётся из `-lang`, затем из `language:` в конфиге, затем из `LC_ALL`, `LC_MESSAGES` или `LANG`; если там нет поддерживаемого, интерфейс на английском. `:lang ru` и `:lang en` переключают язык на ходу и перерисовывают открытые экраны; в конфиг выбор не записывается.

Переведено всё, что пишет сам homer-tui. Имена из Homer и SIP остаются как есть: пути API, профили вроде `1_call`, поля маппингов, SIP-методы, заголовки и причины ответов, значения из базы. Каталог лежит в `internal/homer/locale_ru.go`; тесты `internal/homer` падают, если у помеченной строки нет перевода, в каталоге лишний ключ, у перевода другие `%`-глаголы или текст уходит в ошибку или строку статуса без `T()`.

## Что умеет API homer-app

По исходникам [sipcapture/homer-app](https://github.com/sipcapture/homer-app) (`router/v1`, `controller/v1`, `data/service`). Все пути начинаются с `/api/v3`.

| Группа | Эндпоинты | В homer-tui |
|---|---|---|
| Вход | `POST /auth`, `GET /auth/type/list`, OAuth2 `/oauth2/*` | вход, `:info` |
| Поиск | `POST /search/call/data`, `/search/call/message`, `/search/call/decode/message` | `:calls` и другие |
| Звонок | `POST /call/transaction`, `/call/report/qos`, `/call/report/log` | экран звонка |
| Экспорт и импорт | `POST /export/call/messages/pcap`, `/export/call/messages/text`, `/import/data/pcap[/now]` | `p`, `t`, `:import` |
| Маппинги | `/mapping/protocol` (CRUD), `/mapping/protocol/:hepid/:profile`, `/mapping/protocol/reset[/:guid]`, `/smart/search/tag/:hepid/:profile` | `:mappings` |
| Настройки | `/alias`, `/users`, `/token/auth`, `/advanced`, `/hepsub/protocol`, `/user/settings`, `/agent/subscribe`, `/dashboard/*` | одноимённые команды |
| Служебное | `/users/profile`, `/database/node/list`, `/modules/status`, `/admin/profiles` | шапка, список хостов, `:info` |
| Прокси | `/prometheus/*`, `/search/remote/*` (Loki), `/proxy/grafana/*`, `/statistic/*` (InfluxDB) | нет |
| Живой поток | `GET /ws` (websocket, HEP relay) | нет |

Что учтено в клиенте:

- В `param.location.node` нужно передавать узлы БД (`value` из `/database/node/list`), иначе поиск вернёт пустой результат.
- `timestamp.from/to` задаются в миллисекундах.
- Поиск возвращает отдельные сообщения, а не звонки; группировку по Call-ID делает homer-tui.
- Изменение алиасов, маппингов, hepsub, глобальных настроек, токенов, а также создание и удаление пользователей требует прав администратора.
- Секрет нового API-токена сервер показывает один раз, в ответе на создание.
- Импорт PCAP работает, только если на сервере включён `decoder_shark` и установлен tshark; иначе любой файл получает «bad pcap data».
- Версии homer-app в API нет.

## Эмулятор

`homer-tui-mock` имитирует homer-app со сгенерированным трафиком: звонки через SBC и PBX с разными исходами, регистрации, RTCP, HEP-логи, настоящий PCAP при выгрузке, настройки с созданием, правкой и удалением. С ним можно попробовать homer-tui без Homer, на нём же идут тесты.

```sh
make demo-homer                                      # держать запущенным
./bin/homer-tui -config bin/homer-mock-etc/homer-tui.yaml
```

`make demo-homer` запускает `homer-tui-mock -listen 127.0.0.1:9080 -confdir bin/homer-mock-etc`. Он пишет конфиг с четырьмя хостами на эмуляторе: `lab` входит по паролю, `lab-token` по API-токену (изменения настроек отклоняются, как в homer-app), у `wrong-password` вход не проходит, `down` не отвечает. Эмулятор печатает команду, которая запускает homer-tui с этим конфигом. Всё, что он генерирует, вымышлено: номера, `example.com`, частные адреса.

Тесты идут против эмулятора (`make test`), включая тесты интерфейса на виртуальном экране.

Неофициальный инструмент, не связан с QXIP и sipcapture, авторами Homer.
